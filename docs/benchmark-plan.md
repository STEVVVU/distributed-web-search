## Frozen work and correctness

The root links to all documents, `/ranking` is the topic seed, and other pages link to root/seed. Each page has one of16 topics, a unique ID, common terms and eight repeated benchmark tokens. Empty anchors separate text from graph size. Check every title/text/link/term/posting, independent sparse PageRank to1e-13 and unique/topic/common/multiterm/missing queries under both policies. Synthetic precision@10 describes known term labels only.

Fresh fixture/coordinator/worker processes and disk state per cell use16 splits/reducers,60-second job and30-minute build limits. Index timing includes builder spawn through atomic publication. Five repeats reverse worker-count order alternately. After warm correctness queries, Node writes `independent-query-oracle.json` from generator-side text/postings and independent ranks. k6 checks every HTTP200 body against it, including query/terms/policy, complete result order/fields, links, both ranks, lexical/combined score and snippet; numeric tolerance2e-10. Wrong JSON, missing/extra fields or mismatches increment an exact-mismatch Counter with a strict zero threshold. No API answer serves as its own oracle.

## Load and metric boundaries

Full cells offer1/10/100iterations/s for10seconds using exactly256 preallocated/max VUs and one request per iteration. The rotating ten-case mix preserves equal query/policy coverage. Request timeout5seconds, graceful stop10seconds, no redirects. A final1,000-page/two-worker case offers10requests/s for120seconds. Separate `profile` uses the failing5,000-page/one-worker workload at100requests/s for20seconds with V8 coordinator profiling, excluded from reported timing.

Use [official metric definitions](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/). `http_req_duration` and the validated/rejected/failed request Trends measure sending+waiting+receiving for issued requests, excluding connection/setup and unsent iterations. They are **not scheduled-to-completion latency**. `iteration_duration` also includes connection and oracle work. [Dropped iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/) are unsent offers caused by unavailable VUs; never count them as fast responses or hide them in successful tails. Actual offers equal started+dropped. Started requests partition into exact completions, HTTP429/503 rejections and failures, with timeout counts separately retained. Native HTTP/error/status samples remain in gzip JSON. Native empirical percentiles from small populations do not establish a reliable p99.

Every load retains native `*-summary.json`, `*-raw.json.gz`, log and Linux GNU time CPU/peak-RSS receipt. Node does not calculate request percentiles. Existing coordinator/worker one-second resources and source/runtime/config remain. Inspect generator CPU/RSS and iteration duration beside server profile/resources before attributing a limiter; complete oracle checks also cost generator work. A generator limit makes server capacity inconclusive. Network metrics follow k6's documented boundaries.

Counted overload/HTTP/transport failures/drops do not abort later cells. `measurementComplete` and `correctOutputs` describe execution/data integrity, while `zeroLossEnvelope` is false for any lost offer. The verdict explicitly reports overload. Green workflow does not imply zero-loss SLO. Build/oracle/cleanup failures remain fatal. Preserve the initial5000-page overload failure without rewriting its verdict or inventing an improvement.
