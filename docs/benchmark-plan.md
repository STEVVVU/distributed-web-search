# Frozen owned-graph benchmark v1

Test claim: index wall time/pages per second and end-to-end scheduled HTTP query latency across32/1,000/5,000 owned pages and1/2/4 worker processes. This is a single-host process-scaling test of bounded synthetic documents. It does not establish arbitrary-web crawl capacity or human relevance. No improvement claim is accepted before identical repeated baseline/fix evidence and a source-mapped separate profile exist.

Use Node25 and `npm ci`. First run `node tools/test-search-build-config.mjs`, `node tools/test-search-load-summary.mjs`, `npm run verify` and `node tools/benchmark-search.mjs --smoke`. Full command is `node tools/benchmark-search.mjs`. `--profile` runs a separate5,000-page/one-worker case with coordinator V8 profiling and100requests/s for20seconds. This matches the first observed overload workload. Raw logs, per-process one-second CPU/RSS/page-fault/context-switch counters, complete raw query samples, snapshots and cleanup evidence survive under ignored `.runs/benchmark-*`. `BENCH_OUTPUT` selects a fresh directory. The manual workflow selects `benchmark` or `profile`, defaulting to the full benchmark. No network outside owned loopback is used by the benchmark.

The exact corpus uses a root that links to all remaining documents, a `/ranking` topic seed, and remaining pages linking to root and seed. Every page contains a topic among16, a unique ID, common terms and a fixed eight-token body. Empty anchors keep linked text independent of graph size. Crawl/index/global-and-topic rank execute the actual MapReduce jobs and publish the real snapshot. All titles, text, links, terms and postings are compared with a generator-side oracle. Sparse independent PageRank is iterated to1e-13 and compared against every persisted rank. Exact unique/topic/common/multiterm/missing queries are checked under both policies. Precision@10 is only known synthetic term relevance; it cannot support a general search-quality claim.

Each matrix cell starts a new fixture, coordinator, durable directory and workers; builder uses16 splits/reducers,60-second job and30-minute build bounds. Partitions are held constant across worker counts. Five repeats reverse worker-count order on alternating repeats. Timing starts before builder spawn and includes crawl, both rank profiles, indexing and durable publication; downloads/setup are absent. Every completed cell warms the query path with correctness queries, then offers1/10/100 requests/s for10 seconds each. Offers use an absolute schedule; arrival-to-completion latency includes generator lateness. A256-in-flight generator ceiling records rejected offers, never silently waits. Every HTTP response and entire result order must be correct. Count offers/completed/failed/rejected/timed out and report p50/p95/p99/min/max, bytes and generator event-loop/CPU. Query mixes alternate both policies across the five queries. Queries return complete matching result lists as the shipped service does, including large common-term responses. The final1,000-page/two-worker case sustains10requests/s for120seconds. Each cell stops workers/coordinator, restarts the real coordinator and checks retained query order with restart wall time.

The manual workflow permits300minutes; the harness has a270-minute hard ceiling and checks10GiB reserve before each cell. Build failures, incorrect completed outputs and cleanup failures fail the campaign and retain evidence. Every successful response checks independently computed URL order, title/text, lexical score and global/topic rank. Counted overload, HTTP failures, transport failures, timeouts and generator-ceiling rejections remain in raw records and do not abort subsequent cells/repeats. Completed, failed and rejected latencies are separate. `measurementComplete`/`correctOutputs` describe benchmark execution, while `zeroLossEnvelope` is false whenever any offer was lost; `verdict` explicitly says `measurement-complete-with-overload` when applicable. A successful workflow is not a zero-loss SLO claim. The initial failed hosted run39728812546 remains baseline evidence of5,000-page/100requests/s overload and is not rewritten as success. A4MiB build RPC limit or crawler byte/deadline boundary remains real failure evidence; the harness does not widen it. Process resource preloading is instrumentation and adds small cost equally to every cell. Profiling is separate from reported measurement. Inspect builder per-job timing, coordinator/worker profiles, disk growth, CPU/RSS and client lag before attributing the limiter. Report median/range across five repeats and source/config/hash with each result; claims remain inconclusive if generator saturation or untuned configuration dominates.

Builder settings retain legacy defaults. `SEARCH_MAX_PAGES` allows1..5000(default32); `SEARCH_MAX_DEPTH`0..16(default4); `SEARCH_SPLITS`1..64(default4); `SEARCH_REDUCERS`1..64(default2); `SEARCH_JOB_TIMEOUT_MS`100..60000(default15000); `SEARCH_BUILD_TIMEOUT_MS`1000..1800000(default180000). Loopback origin enforcement,2-second per-page fetch,256KiB HTML cap,4MiB RPC cap, URL/term limits, task fencing and atomic publication are unchanged. `tools/test-search-build-config.mjs` checks defaults and invalid/minimum/maximum values. No third-party data/code was adopted.
